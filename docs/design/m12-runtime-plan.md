# M12 plan: runtime, bytecode format and performance

Status: **Plan with decisions made (2026-11-14). Slices 1 and 2 are started; nothing else is implemented.** Written
2026-11-09. It follows [ROADMAP M12](../ROADMAP.md) (goal, deliverables, exit criteria) and takes the lessons of M11 as
constraints. The plan itself is not independently reviewed. The owner decided D1 to D7 and the open questions of section 7
on 2026-11-14; section 3 records each decision and where it changed the recommendation.

## 1. What M12 is for

Make execution fast, repeatable and portable, and decide with evidence whether a native runtime is warranted. The milestone
**ends in a decision document, not a new runtime.** Four deliverables from the roadmap: a versioned bytecode format with a
specification and load-time `verify()`, a compiled-artifact cache, a benchmark suite tracked in CI, and a written evaluation of
native or alternative runtimes.

### Non-goals

* A new language feature, a change in what any program prints, or a change in an error message. Every conformance case, on
  every engine, passes unchanged at every step of M12.
* A native runtime. M12 evaluates one; building it is a separate milestone if the decision says so.
* Making the tree-walker or the self-hosted interpreter faster. They stay the references for differential testing (the
  tree-walker) and for self-hosting (the self-hosted interpreter).
* Sharing the Godot port's bytecode (`nova_opcodes.gd`, the game dialect). It is a separate instruction set for a separate
  language profile; section 3, decision D5.

## 2. Where things stand (facts, checked on `main` after M11)

* The compiler (`novalang.py`, AST to `CodeObject`) emits **66 opcodes** (`OPCODES`). A `CodeObject` holds `ops`, `args`,
  `positions`, `constants`, `exception_table`, slot and parameter data, free variables and closure layout.
  It exists **only in memory**: there is no serialized form and nothing is cached between runs.
* `verify(code)` exists and checks jump targets, slots, constants, falling off the end and stack-depth agreement. `--dis`
  prints bytecode. `tests/compiler/` and `tests/vm/` test the compiler and the VM; the differential station compares the VM to
  the tree-walker.
* `tests/bench/` has four programs (`fib22`, `loops`, `closures`, `index_assign`) and `run_bench.py`. The README says the VM is
  faster on every one of them; the numbers are not generated by anything, not tracked, and not run in CI.
* **What M11 fixed that M12 must not break.**
  * Compiled code is **independent of the profile**: a gated name compiles to `LOAD_BUILTIN` and is resolved when the program
    runs, so one artifact is right for a `trusted` and a `restricted` engine. A cache keyed on the source (and not on the
    profile) is therefore valid for both, and must stay so.
  * The **step budget counts one loop pass or one call.** A fast path that fuses, removes or adds a counted event changes what
    a budget of N steps means and is a behaviour change, not an optimisation.
  * The fatal limits (`FatalLimit`, a `BaseException`) are checked between steps; the time limit cannot interrupt one C-level
    call (the review package, section 6). A fast path must not make a loop body un-interruptible.
  * The 201-cell coverage matrix is per engine. A new engine is 67 new cells to cover, not a free addition.
* D-045 (the self-hosted interpreter had no type gate in `restricted`) was deferred to M12 by ADR 0005 and **closed before M12 started** (2.2.0): the launcher's type-check walk takes the import grants. Slice 7 below is therefore withdrawn.

## 3. Decisions (made by the owner, 2026-11-14)

All seven recommendations were accepted. **Two carry a change or a caveat**, marked below and in the table:

* **D1 correction: no list or dictionary constants.** The first draft allowed "list/dict of those". On 2026-11-11 the owner
  approved six design choices for the draft chapter 17, one of which is *no list or dictionary constants*. That approval
  is later and safer (fewer shapes for the loader to read, no nesting of containers inside constants), so it wins: the closed
  set of constant types is **nothing, boolean, number, string and a nested code object**. A program that needs a list builds it
  with `BUILD_LIST`. Slice 3's `[bc.constants]` and slice 4's loader follow this.
* **D4 caveat: the cache helps start-up, not execution throughput.** A cache removes lexing, parsing and compiling and nothing
  else. The proof-of-concept apps spend their time executing: Nova_Data's 10,000 rows take about two seconds and compiling its
  670 lines is a rounding error beside that. Slice 5 must therefore not be sold, or measured, as a speed-up of running
  programs; its exit criterion is a warm start-up of a module-heavy program, and the throughput targets belong to slice 6.
  The baseline of slice 1 reports start-up and execution separately for this reason.

* **D7 first result (2026-11-14): PyPy runs the unmodified VM 9x to 14x faster on a warm run and 2.7x to 2.9x on a cold first run of a 0.5 to 0.7 s program
  (8.7x on a 13 s one), but starts 3.4x slower.** Output is identical. Details and limits in
  [`docs/benchmarks.md`](../benchmarks.md), section "D7, first measurement". **The test suite does not pass on PyPy yet:** at NovaLang's recursion limit of 20,000 PyPy crashes (segmentation fault) on a deeply nested program
  where CPython gives the named nesting error, and with the limit capped at 10,000 two nesting cases of the conformance corpus fail because PyPy runs the
  program instead of refusing it (all other checks run pass). The nesting limit leans on CPython's `RecursionError`; making it explicit in the parser,
  compiler and tree-walker is a prerequisite for any non-CPython engine, logged as [G-051](../GAPS.md), and decided on 2026-11-14 for slice 6 or earlier. Until then PyPy is a measurement,
  not a supported engine, and a new engine may not carry the `restricted` name until the 201 cells pass on it (section 4, slice 8).

## 3a. The decisions as proposed

| # | Decision | Recommendation (accepted; D1 changed, see above) | Why |
| --- | --- | --- | --- |
| D1 | The serialized form | A **purpose-built, versioned, length-prefixed binary** format written and read by explicit code. Not `pickle`, not `marshal` | A loader that executes or reconstructs arbitrary objects turns a poisoned cache file into code execution outside every grant. Explicit reading of a closed set of constant types (nothing, boolean, number, string, nested code object; **no list or dict constants, per the owner's decision of 2026-11-14**) cannot |
| D2 | Version policy | A format version (breaks the layout), an **opcode-set hash** (changes when any opcode's meaning or numbering does) and the compiler's version string in the header; a loader accepts only a format version it knows and an opcode hash it matches, and otherwise **rejects with a named error and recompiles** | The exit criterion is "accepted or cleanly rejected", never "misread" |
| D3 | Is the bytecode format part of the M13 stable API? | **No.** It is versioned and specified so that it can be verified and cached, and the policy says the format may change in any minor release. Only "an artifact is accepted or rejected, never misread" is promised | Freezing an instruction set before the fast paths of slice 6 is premature |
| D4 | Where the cache lives, and who may write it | Per-user cache directory (`$XDG_CACHE_HOME`, `%LOCALAPPDATA%`, `~/Library/Caches`), created with the user's permissions only; refuse a directory writable by others; `--no-cache` and `NOVALANG_CACHE=off`. **Off by default in `restricted`** unless the embedder passes a cache directory | A cache another account can write is a code-injection path. A restricted program must not choose where it is written |
| D5 | Does the GDScript port share the format? | **No**, in M12. Document the mapping of opcodes and keep `nova_opcodes.gd` independent. Revisit when M13 defines what the game dialect shares | Different value model (Variants), different profile, owned by another repository |
| D6 | How benchmark numbers are tracked | Relative, not absolute: each CI job measures a fixed set of programs several times, reports the **median and the spread**, and compares with the median of the same job on the default branch; an alert needs both a margin (e.g. 15 %) and a spread smaller than the margin. History is kept as CI artifacts and in a generated `docs/BENCHMARKS.md` | Shared runners are noisy; an absolute threshold either never fires or always does |
| D7 | The native-runtime candidates to evaluate | PyPy; compiling `novalang.py` with mypyc or Cython; a C or Rust port of the VM loop behind the same artifact format; WebAssembly; staying as is with fast paths only | Section slice 8 |

## 4. Slices

Each slice is a branch and a PR, with the project's rules: a full local suite, one full CI matrix per pushed commit, a PR only
when green, no merge without the owner's go-ahead, documents labelled with their review state.

### Slice 1: a baseline and the benchmark suite

**Status (2026-11-14): built; the baseline is in [`docs/benchmarks.md`](../benchmarks.md).** What exists now: `tests/benchmarks/run.py`
gained a `workloads` group (`tests/benchmarks/suite.py`): 15 micro programs (11 new, the 4 older `tests/bench/` ones), and the
real programs of three proof-of-concept apps (Nova_Data, Nova_Log, Nova_Stats), vendored under `tests/benchmarks/workloads/`
with seeded generators; each runs in-process on the VM under `trusted` and under `restricted`, so the cost of M11 is a number
per program; `--full` adds the 50 MB Nova_Log run; every row carries the compile share (decision D4's caveat). Not yet in:
the reactor's policy-dialect tick loop, the CI job and the generated `docs/BENCHMARKS.md`.

* Start from `tests/benchmarks/run.py`, which exists before M12 and already measures cold start-up, the front end by stage, a tight
  loop on the VM, the tree-walker and the `restricted` profile, and the embedding API, and records its baseline in
  `docs/benchmarks.md`. Grow `tests/bench/` and it from four programs to about a dozen that cover what programs do: recursion (`fib`), loops and arithmetic,
  string building, list and dictionary work, closures, `map`/`filter`/`reduce`, a module-heavy start-up, `try`/`catch` in a loop,
  and the policy-dialect tick loop of the reactor (the 900-step trace is a real workload).
* `python3 tests/benchmarks/run.py --json` is the one command: runs each program N times after a warm-up on each engine and
  both profiles, reports median, minimum and spread, the machine and Python version, and the commit.
* **Measure the cost of M11 itself**: `restricted` against `trusted` on every program, so the price of the limit checks is a
  number in the report and a regression is visible.
* A `bench` CI job (not required for merge at first) uploads the JSON. Writes `docs/BENCHMARKS.md` from the data; the README's
  numbers are replaced by a link and a generated table.
* Exit: the command runs in under five minutes on a CI runner, twice in a row within the stated spread.

### Slice 2: a profile of where VM time goes

**Status (2026-11-14): done; the result is [`m12-vm-profile.md`](m12-vm-profile.md)** (`tests/benchmarks/profile_vm.py` and
`op_costs.py` reproduce it).

* An opcode histogram and a per-opcode time estimate (a counting build of the dispatch loop, not a sampling profile of Python,
  which reports the loop and nothing else), per benchmark; the top call sites in `call_value`, `binary_operation` and the
  frame set-up; allocation counts.
* Output: `docs/design/m12-vm-profile.md`, a table of where the time goes and a ranked list of candidate fast paths with the
  share each could win. Nothing is changed in the VM.
* Exit: the ranked list names at least three candidates with a measured upper bound each.

### Slice 3: the bytecode specification (`docs/spec/17-bytecode.md`)

**Status (2026-11-14): done. The chapter is [`docs/spec/17-bytecode.md`](../spec/17-bytecode.md), normative, with 72 conformance cases (profile `bytecode`) citing all twelve of its sections.**
It is implemented (slice 4) and its decisions are the owner's. What did not move: the cache rules (`[bc.cache]`), the findings and the nine questions stay in
[`m12-bytecode-notes.md`](m12-bytecode-notes.md), because a case is a program and its result and no case can pin a cache directory before slice 5 builds it; `[bc.cache]` joins
the chapter, with its cases, in slice 5. `tests/compiler/test_bytecode_draft.py` (run by the compiler station) keeps the chapter's opcode table, its hash and the table in `novalang.py`
in step with `novalang.OPCODES`. Reading the compiler and the VM for it found six facts the plan did not have (notes, `[bc.findings]`): the compiler's pool holds tuples, lists and `BuiltinFunction`
objects, so those became instruction arguments and a built-in-by-name tag; ungated built-ins are constants, so the loader refuses gated names (an artifact could otherwise carry `read` into an
engine without the grant); `verify()` does not check what the VM trusts (pool indexes, slots inside chains and loop state, closure indexes); a cache hit would skip the type gate unless the
artifact records whether the source has annotations or imports; a 400-digit float literal compiles to infinity (G-052); and nesting depth leans on CPython's recursion limit, which PyPy
breaks (G-051).

### Slice 4: the serializer, the loader and the compatibility corpus

**Status (2026-11-14): built** (`dump_artifact`, `load_artifact`, `--compile`, `--check-artifact`, running a `.novac`; `tests/bytecode/`, a station of `run_all.py`).
It follows the owner's nine decisions (the format embeds its source; development builds write version 0; limits as proposed; no compression; no cache on Windows by default;
`InternalError` exit 70). Measured: reading and verifying is 2.5x to 3.0x faster than compiling (`docs/benchmarks.md`). The chapter's conformance cases are done (slice 3's section); the cache is slice 5.

* `dump(code) -> bytes` and `load(bytes) -> CodeObject` in `novalang.py`, plus `--compile file.nova -o file.novac` and running
  a `.novac` directly. `load` calls `verify()` and rejects with the errors of `[bc.reject]`.
* **A corpus of artifacts**, like the conformance corpus: golden `.novac` files produced by this version, committed under
  `tests/bytecode/fixtures/v1/`, with the expected result of loading them. Every later version must load them or reject them
  cleanly; a CI station fails if it does neither. This is the test of the exit criterion "bytecode produced by one version is
  accepted or cleanly rejected by another".
* Corruption tests: every prefix of every fixture (truncation), every single-byte change (flipped constant type, jump target,
  length), and random mutations from a seeded fuzzer. The invariant: `load` returns a verified `CodeObject` or raises the named
  error, never another exception, and never a `CodeObject` that `verify()` would reject.
* Round trip: for every program of the conformance corpus, compile, dump, load and run gives the same output, error and exit
  as compiling and running directly, on the VM, with both profiles.

### Slice 5: the compiled-artifact cache

**Status (2026-11-14): built.** `ArtifactCache` in `novalang.py`, `--cache-dir`, `--no-cache`, `NOVALANG_CACHE`; the rules are `[bc.cache]` of
[chapter 17](../spec/17-bytecode.md), pinned by 17 conformance cases and 25 tests; threat T17 is in the M11 threat model (unreviewed). Measured: a warm start of Nova_Stats'
21 modules is 14% faster (`docs/benchmarks.md`), a hit costs about 3.6 ms before it saves. Left out on purpose: eviction (Q6), the Windows cache (Q5). Not done: the cache has not run
on Windows, Python 3.7 or PyPy.

* Key: source hash, format version, opcode-set hash, compiler version. Not the profile, not the limits (M11: code is
  profile-independent), not the working directory.
* Behaviour per D4; `--no-cache`, `--cache-dir`, `NOVALANG_CACHE`; a module import uses the cache as the main program does, keyed on
  the module's own text.
* Tests: a hit gives byte-identical behaviour (the corpus runs twice, cold and warm, and must agree, including line numbers in
  errors); a corrupt, truncated, foreign or newer file is ignored and replaced; a cache directory that others can write is
  refused; a read-only directory does not fail the program; concurrent runs do not corrupt each other.
* **Security addendum to the M11 threat model** (a new threat T17: a poisoned cache): the loader reads a closed set of types and
  verifies, so a poisoned artifact can do what a program can do under the loader's profile and nothing more; the cache is still
  an input the embedder must keep private. The `restricted` rule of D4 is tested.
* Exit: a warm start-up of a module-heavy program is measurably faster (the number goes in the benchmark report).

### Slice 6: targeted fast paths

Only those the slice 2 profile ranks, each its own commit with: the benchmark evidence (before and after, with spread), the
differential station (VM against the tree-walker) and the full conformance corpus, and the **M11 invariants as tests**:

* the step count of every escape-corpus and limit program is unchanged (a test records the exact step total of a set of
  programs on the VM before M12 and requires it to stay equal);
* every fatal limit still trips in the same position of the same programs;
* `restricted` and `trusted` still run the same compiled code.

Candidates to examine, not commitments: superinstructions for the common `LOAD_FAST`/`LOAD_CONST`/arithmetic pairs; avoiding the
argument tuple in calls to user functions; caching the global and builtin lookups per code object; a cheaper frame for leaf
functions; specialising `for` over a range. A fast path that needs a changed step count or a weaker check is dropped, not
negotiated.

### Slice 7: withdrawn (D-045 was closed in 2.2.0)

The self-hosted interpreter now type-checks the program and the modules inside the import grants without reading anything outside
them, so there is nothing left to decide here. One question stays for slice 4 or 5: if the artifact loader ever feeds the
self-hosted interpreter, its `restricted` launcher must keep the same rule (judge a module by its real path before opening it).

### Slice 8: the evaluation of native and alternative runtimes (the decision document)

`docs/design/m12-runtime-decision.md`, with a criteria table and measurements, not opinions:

* what the ecosystem would gain: the benchmark speed-up on the slice 1 programs, start-up time, memory, deployment size, and
  portability (the CI matrix covers Python 3.7 to 3.13 on three operating systems; what does each candidate cover?);
* what it would cost: build and release complexity, a second implementation of the language to keep equal to the specification
  (every conformance case, **and the 67 rows of the sandbox matrix**, would have to pass on it, so a new engine is not
  allowed to carry the `restricted` name until they do), the effect on the reviewer's work (the independent review of M11 reads
  Python), and who maintains it;
* the candidates of D7, each measured where it can be (PyPy and mypyc can be tried in a day; a C or Rust loop is estimated, with
  the estimate's basis stated);
* a recommendation: build, do not build, or build later with the trigger that would make it worth it. The document is reviewed by
  the owner before the milestone closes.

### Slice 9: close-out

README numbers generated from the suite; `docs/BENCHMARKS.md`; CHANGELOG; ROADMAP status; DEVELOPMENT_STATUS counts; the
bytecode chapter cited by the conformance station; any M11 document that changes (the threat model's T17) re-labelled with
its review state.

## 5. Exit criteria (testable)

1. Bytecode produced by one version is accepted or cleanly rejected by another: the fixture corpus of slice 4 passes in CI on every
   platform, and the corruption fuzzer finds no input that loads unverified or raises an unnamed error.
2. Benchmarks are reproducible from one command (`python3 tests/benchmarks/run.py --json`) and run in CI, with the spread
   reported and regressions alerted by the rule of D6.
3. Every conformance case and every cell of the sandbox matrix passes unchanged, on all engines, after every slice. The
   step totals recorded in slice 6 are unchanged.
4. The README's benchmark numbers are generated, not typed.
5. The native-runtime decision document exists, has measurements, and has a recommendation the owner has read.
6. No document says more about security than `[sbx.claims]` allows (the wording test passes), and the threat model records the cache.

## 6. Risks

| Risk | Mitigation |
| --- | --- |
| Benchmark noise on shared runners hides or invents regressions | D6: relative comparison, medians and spread, an alert needs both; run the baseline and the candidate on the same job |
| A fast path quietly changes step counts, so sandbox budgets mean something else | Slice 6's recorded step totals are a test; a changed total fails the slice |
| A fast path makes a loop un-interruptible, widening the "time is checked between steps" gap | The time and step checks stay at the same events; the escape corpus's fatal-limit cases run against every fast path |
| A poisoned or corrupt cache | D1 and D4: closed-set loader, `verify()`, private directory, off by default in `restricted`, corrupt file means recompile |
| Freezing the format early | D3: the format is versioned and may change in a minor release; only accept-or-reject is promised |
| The format works on 3.12 and breaks on 3.7 (integer, float or string encoding, `struct`, hashing) | The fixture corpus is loaded on every job of the 12-job matrix, including Windows 3.7 |
| Time goes to speed and not to the decision | The milestone ends in slice 8's document; slice 6 stops when the profile's ranked list is exhausted or a candidate fails its evidence |

## 7. Open questions, answered by the owner on 2026-11-14

1. **D1 to D7:** accepted as recommended, with the D1 correction and the D4 caveat of section 3.
2. **May a regression alert block a merge?** Warn first; block only after a month of data.
3. **Cache on by default for the command line?** Yes for `trusted`, as D4 describes, with `--no-cache`; off in `restricted`.
4. **Which workloads decide the order of fast paths?** The reactor loop and the proof-of-concept workloads (Nova_Data, Nova_Log,
   Nova_Stats), which slice 1 now measures.
5. **Does the independent reviewer of M11 also read the loader?** Yes: it is a new parser of untrusted input.

## 8. Order and size

Slices 1 and 2 first (they decide what the rest is for), then 3 and 4 (the specification and the loader), 5 (the cache), and 6 and 7
in parallel; 8 can start after slice 1 and must finish before 9. Relative size, as in the roadmap: L.
