# Benchmarks

Baselines that milestones are measured against. The M12 baseline below is generated by `tests/benchmarks/run.py`; the older
"Real-World Baseline (Pre-M12)" further down was typed in from the proof-of-concept repositories' own reports. Per-app detail and
reproduction steps live in each proof-of-concept repo (Nova_Stats, Nova_Sort, Nova_Log, Nova_Data).

## M12 baseline, slice 1 (2026-11-14)

The first numbers produced by the suite itself, not typed in. They are the "before" that every later M12 slice is compared
with (D6: relative to this file, medians and spread, never absolute across machines).

| | |
| --- | --- |
| Machine | MacBook Pro M1, 8 GB, macOS (Darwin arm64), 8 CPUs |
| Python | CPython 3.9.6 (the macOS system Python) |
| NovaLang | 2.2.0, `develop` at `6b16c4a` plus the uncommitted M12 slice 1 and 2 files |
| Engine | the bytecode VM (the default); the tree-walker appears only in the loop group |
| Command | `python3 tests/benchmarks/run.py --full --repeat 9 --json OUT.json`, run twice in a row (`workloads` use at most 5 samples) |
| Raw data | [`tests/benchmarks/baselines/2026-11-14-run1.json`](../tests/benchmarks/baselines/2026-11-14-run1.json) and `-run2.json`: every sample of every row |

**Reproducibility (the slice 1 exit test).** Run 2 repeated run 1's medians within 3% on 44 of the 56 rows and within 5% on
54. Of the 38 workload rows, 35 agree within 3% and the worst is 4.3% (the 35 ms module start-up, a short row). The two
rows that differ by more than 5% are whole-process start-up measurements (`--tree-walk` 12%, `--profile restricted` 11%),
where spawning a process is the noise. The longest row (the 50 MB log, three samples) differed by 3.2%. Apart from that
50 MB row, the rows that differ by 3% to 5% are short or process-level. So treat a difference under about 4% as noise on
programs that run for more than half a second, and under 5% on the rest. The whole suite takes about five minutes a run.

### Workloads

Each workload ran in-process on the VM under `trusted` and under `restricted` (M11's limit checks on; limits raised only
where a program needs more steps or time, never lowered). `compile share` is the lex + parse + compile time of the
program as a share of its run time: **the most a bytecode cache could remove from that row** (D4's caveat, measured).
A module-heavy start-up row counts only the main file's compile, so its share understates what a cache saves there.

What the table says:

* **Execution, not start-up, is where PoC time goes.** The compile share of every PoC program is 0.1% to 5%
  (the 5% is the 0.9 MB log, which runs for a quarter of a second). A cache cannot move a throughput number; slice 6 can.
* **Nova_Log reproduces the pre-M12 figure** (24,165 lines/s here against 24,500 in the table below); **Nova_Data** reproduces
  5,857 rows/s against 5,916; **Nova_Stats** costs 13 ms a tick on the VM against 11 ms.
* **The price of `restricted` varies from nothing to +83%.** It is 3% to 9% on loops, recursion, indexing and closures, but
  +40% to +83% on programs that call library functions or build strings (`string building` +83%, `split/trim/upper/join` +60%,
  `float math` +49%, `list append` +40%). The limit checks run at every library call and every string `+`; this is the
  M11 cost slice 6 must not make worse, and a place it may be able to make better without weakening a check.
* **The real programs sit between:** Nova_Data +18%, Nova_Log +22%, Nova_Stats +33%.
* **The 50 MB Nova_Log run** took 12.8 s (23,708 lines/s, three samples). It runs only under `trusted`: the restricted
  profile refuses a string over 1,000,000 characters, so the file cannot be read there (G-036).
* The Nova_Stats `restricted` row needs the `regex` grant, only because `replace_all` is defined under it (G-050).

Observations on start-up, not part of the plan's cache:

* A bare `python3 -c pass` took 32.6 ms and `import novalang` 141.5 ms in the baseline runs: **109 ms before any NovaLang program starts**, the
  same for the VM, the tree-walker and `restricted`. A re-check later the same day, on a quieter machine, gave 17 ms and 74 ms: **57 ms**. The
  start-up rows move by up to 2x with the machine's state, so read them against each other, not as absolutes. `python3 -X importtime` shows where
  the time goes: the module's own body about a third, the rest the standard library it imports (`json`, `platform`, `subprocess`, `re`,
  `decimal`). The artifact cache of slice 5 does not touch this; importing those modules only when needed would.
  Not changed here: it is a finding for the slice 5 or slice 6 discussion.
* Lexing 3,545 lines takes 102 ms, parsing 38 ms, compiling 38 ms: **the lexer is 57% of the front end.**
  That is the part a cache removes for a large module (Nova_Stats loads 21 modules, 7% of its run, see the profile).

## D7, first measurement: the same suite on PyPy (2026-11-14)

The plan's decision D7 lists PyPy first because it can be tried in a day with no code change. This is that try: the **unmodified**
`novalang.py` run by PyPy 3.10.16 (installed with `uv python install pypy@3.10`) and by the CPython 3.9.6 of the baseline above, on the
same machine, with the same command (`NOVA_BENCH_WARMUP=3 pypy3.10 tests/benchmarks/run.py --full --repeat 9`: three warm-up runs per row
instead of one, because a JIT needs them). Raw data: [`tests/benchmarks/baselines/2026-11-14-pypy3.10.json`](../tests/benchmarks/baselines/2026-11-14-pypy3.10.json).
The two interpreters are different versions of Python (3.9 and 3.10), so some of the gap is not PyPy's.

**Steady state (the suite: the JIT is warm, each row is the median of its samples):**

| workload | CPython 3.9 | PyPy 3.10 | speedup |
| --- | ---: | ---: | ---: |
| Nova_Log, 5 MB, trusted | 24,165 lines/s | 223,425 lines/s | **9.2x** |
| Nova_Log, 50 MB, trusted | 23,708 lines/s | 235,722 lines/s | **9.9x** |
| Nova_Log, 0.9 MB, restricted | 18,869 lines/s | 143,007 lines/s | **7.6x** |
| Nova_Data, 10,000 rows, trusted | 5,857 rows/s | 50,627 rows/s | **8.6x** |
| Nova_Data, 10,000 rows, restricted | 4,953 rows/s | 43,666 rows/s | **8.8x** |
| Nova_Stats, 50 ticks, trusted | 75 ticks/s | 299 ticks/s | **4.0x** |
| Nova_Stats, 50 ticks, restricted | 56 ticks/s | 317 ticks/s | **5.6x** |

All fifteen micro programs run 1.2x to 14.9x faster (median 11.5x). The tight loop on the VM is 13x, the
lexer 20x, the embedding API 8x to 12x. The slowest gain is `map`/`filter`/`reduce` with callbacks (5.8x) and the 50-tick Nova_Stats (4x trusted,
5.6x restricted). `restricted` gains as much as `trusted` or more: the limit checks are Python code too.

**What a user sees: one process, a cold JIT.** A first run includes the JIT's warm-up, and PyPy starts slower:

| one whole process | CPython 3.9 | PyPy 3.10 | speedup |
| --- | ---: | ---: | ---: |
| an empty program | 0.07 s | 0.24 s | 0.3x (3.4x slower) |
| Nova_Log, 5 MB | 1.41 s | 0.48 s | 2.9x |
| Nova_Data, 10,000 rows | 1.89 s | 0.69 s | 2.7x |
| Nova_Log, 50 MB | 13.26 s | 1.52 s | 8.7x |

Same output, checked: the Nova_Log and Nova_Data reports are identical line for line on both interpreters (only the timing line differs), and
all 15 micro programs and the 4 older benchmark programs print the same text.

What this does and does not tell us:

* **A drop-in 9x to 14x on a warm run is real, and it is far larger than the 20% to 30% that slice 6's three candidates can win together.**
  It changes how M12's evaluation (slice 8) should be framed: the question is no longer "is a native runtime worth building" but "what is the
  cheapest way to put NovaLang's VM on a JIT, for whom, and what does it cost".
* **It does not help the short run.** A command-line program that runs for a few hundred milliseconds is slower under PyPy because of
  start-up (0.24 s against 0.07 s); it breaks even somewhere near a quarter of a second of work and wins clearly past a second. The 5 s time limit of
  the `restricted` profile and a 10,000-row CSV are in the winning zone; a one-line script is not.
* **Not measured yet:** memory (Nova_Log holds about 4x its file in memory on CPython; PyPy's figure is unknown), PyPy's behaviour on the time
  limit's wall-clock checks, and installation: PyPy is not on a user's machine, so this is a speed for those who choose to install it, not a
  speed for NovaLang as shipped.

**Does NovaLang's own test suite pass on PyPy? Almost, and the gap is exactly the sandbox's job (run 2026-11-14, `tests/run_all.py` stations on PyPy 3.10.16).**
The same stations on CPython 3.9.6 are all green (2,029 checks).

| On PyPy | Result |
| --- | --- |
| As it is, `sys.setrecursionlimit(20000)` | **The interpreter crashes with a segmentation fault (exit 139)** on a long chain of `and` (for example 20,000 operands), in `trusted` and in `restricted`; CPython prints `NovaError: the interpreter ran out of stack - recursion too deep`. It aborts the sandbox unit tests at the first such case (`test_esc_parser_nesting_a_long_chain_of_and_vm`, after 87 tests) and the conformance station |
| With the limit capped at 10,000 (an experiment through a `sitecustomize` hook outside the repository; `novalang.py` is unchanged) | The crash is gone. All 256 sandbox unit tests pass (3 skipped); the conformance corpus, the security matrix, the compiler and the type-checker stations pass **1,579 checks and fail 2 cases**: `sbx-limit-nesting` on the VM and the tree-walker, and `esc-parser-nesting-unary-minus` on the tree-walker. In those PyPy neither raises the nesting error nor crashes: **the deeply nested program simply runs and prints its result** |
| Portability station | Timed out at the harness's 300 s on PyPy (about 3.4x slower to start a process, thousands of processes); not investigated |
| Not run on PyPy | the differential station, parity, and the other stations |

So the speed is real and the output matches; what fails is **the resource-exhaustion contract**: a program nested too deeply must get a named error,
never a crash and never a silent success, and today that depends on CPython's recursion limit meaning what NovaLang assumes. On PyPy the same
setting either overruns the C stack (20,000) or does not count the way the corpus expects (10,000). Making NovaLang's own nesting depth explicit in the
parser, compiler and tree-walker, instead of leaning on `RecursionError`, would remove the dependence and is worth doing for CPython as well; it is
logged as [G-051](GAPS.md) and planned for slice 6 or earlier. Until it is done, **PyPy is a measurement, not a supported engine, and must not be offered with the `restricted` profile** (slice 8's rule).

## Real-World Baseline (Pre-M12)

These benchmarks establish the performance and security baseline for the M12 (Bytecode Cache & Performance) and M13 (Libraries) milestones. Run on a MacBook Pro M1 (8GB RAM). Unless noted, engine is the Bytecode VM.

### 1. Nova_Stats (System Telemetry)
- **Throughput:** 11 ms per tick on the VM (649 ms on self-hosted).
- **Memory Profile:** 212 MB peak while sampling six system modules.
- **Findings:** Detected a 100% CPU load spike and memory pressure flip to "warning" caused by parallel Python processes. Established that macOS `pmset` uses a heavily smoothed historical average for battery, while NovaLang correctly calculates instantaneous physics.
- **Gaps:** G-026 (Ctrl-C traceback in embedding API).

### 2. Nova_Sort (Sandbox & File I/O)
- **Throughput:** Instantaneous for a 5-item folder. 
- **Security Baseline:** The sandbox successfully enforced `files.read` and `files.write`. However, it revealed two critical flaws: `files.write` implicitly grants `remove`/`delete` (G-027), and `rename` silently overwrites existing files (G-028). 
- **Findings:** Because the sandbox could not prevent deletions or overwrites, the `Nova_Sort` program had to implement its own safety layer (forbidding delete keywords and checking `exists()` before renaming) to safely manage file system operations.

### 3. Nova_Log (Text Parsing at Scale)
- **Throughput:** Consistent ~24,500 lines/sec across all datasets.
- **Memory Profile:** 212 MB peak for a 50 MB file (proves G-036: no streaming read).
- **Datasets & Results:**
  | Dataset | Lines | Time | Unparsed | Notes |
  |---|---|---|---|---|
  | Sample access log (May 2015) | 10,000 | 0.42s | 0 | Combined log format; 10,000-line sample file, dated 17 May 2015 |
  | Synthetic (Tesla/Starlink) | 50,000 | 2.05s | 0 | 50/50 split of 200s/404s |
  | Nginx (Modern) | 51,462 | 2.09s | 0 | 6.8MB file, universal parsing |
- **Sandbox Limit:** Refused a 1.1MB file with `a string cannot grow beyond 1000000 characters`. Successfully parsed a 488KB chunk (2,154 lines) in the sandbox.

### 4. Nova_Data (Financial Math)
- **Throughput:** 5,916 records/s (1.69s for 10,000 rows).
- **Dataset:** 10,000 synthetic financial transactions (CSV).
- **Precision Baseline:** 
  - Exact sum (integer cents): `$2,231,316.93`
  - Naive float sum (via `str()`): `2231316.930000008`
  - **Drift:** `$0.000000008` after 9,993 additions (Proves the requirement for exact decimal math, G-044).
- **Resilience:** Successfully rejected 6 corrupted rows (leap year 2025-02-29, `N/A` text, `4.999` fraction, missing fields, month 13) without crashing.
- **Sandbox:** Successfully processed a 700KB CSV in `restricted` mode with `--allow-read data`.

### Summary for M12
The core bottleneck across all PoCs is the VM interpreter's overhead when handling string manipulation, floating-point conversions, and massive memory allocations (e.g., reading whole files into memory). The lack of native `regex`, `index`, and streaming reads forces NovaLang to do heavy lifting in the interpreter rather than in optimized C-level standard library functions.
